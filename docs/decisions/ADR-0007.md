# ADR-0007: Adjacent-to-Spec-Kit Positioning

## Status

- Accepted

## Context and Problem Statement

The conventional-agents repository is positioned as a complementary layer to the Spec Kit (workflow orchestration framework). Both provide guidance and standards, but they serve different purposes:

- **conventional-agents:** Quality standards, role contracts, testing guidelines, integration rules.

- **Spec Kit:** Workflow orchestration, multi-step coordination, .specify/ directory structure.

Without clear boundaries, there is a risk of:

- **Scope creep (HIGH impact, MEDIUM probability):** conventional-agents could expand into workflow orchestration, creating competition or confusion with Spec Kit.

- **Dependency entanglement:** conventional-agents could become tightly coupled to .specify/ internals, breaking if Spec Kit changes.

- **Duplicate functionality:** Both projects could end up documenting the same workflows or decision patterns.

- **Unclear integration:** Host repos wouldn't know where responsibilities end for one project and begin for another.

The core problem: How do we clearly delineate the scope of conventional-agents so that it remains a complementary quality and standards layer, not a competing workflow engine?

## Decision Drivers

- **Specialization:** Each project should excel at its core mission without overreach.

- **Complementarity:** conventional-agents and Spec Kit should enhance each other, not compete.

- **Maintainability:** Clear boundaries reduce coupling and make maintenance easier.

- **Adoption:** Teams should understand what conventional-agents offers without fear of lock-in or conflict with Spec Kit.

- **Sustainability:** conventional-agents should remain valuable even if Spec Kit changes or is not used.

## Considered Options

### Option A: Expand conventional-agents Scope to Include Workflow Orchestration

conventional-agents becomes a full-featured workflow orchestration system, replacing or competing with Spec Kit.

**Pros:**

- Single entry point for all agent guidance and orchestration

- Potential for more integrated features

**Cons:**

- Directly conflicts with Spec Kit's mission

- Massive scope expansion, beyond current goals

- Duplicates work already done by Spec Kit

- Creates confusion about which tool to use for what

- Maintenance burden becomes unsustainable

- Team would need entirely different expertise (orchestration vs. standards)

- HIGH risk of incomplete implementation and abandonment

### Option B: Stay Strictly Adjacent – Standards Only, Never Orchestration (CHOSEN)

conventional-agents provides quality standards, role contracts, testing guidelines, and integration rules. It never orchestrates workflows, modifies .specify/, or competes with Spec Kit. Spec Kit is the authoritative source for workflow orchestration.

**Pros:**

- Clear, focused mission for conventional-agents

- Minimal risk of conflict with Spec Kit

- conventional-agents remains lightweight and maintainable

- Natural division of labor: Spec Kit handles "what happens next?", conventional-agents handles "is this correct?"

- Teams using Spec Kit can confidently adopt conventional-agents without redundancy

- Lower barrier to entry for maintainers (standards vs. complex orchestration)

**Cons:**

- Some workflows may require coordination between conventional-agents and Spec Kit (mitigated by integration docs).

- Teams must understand two separate systems (mitigated by clear documentation of the boundary).

### Option C: Fork or Replace Spec Kit

conventional-agents replaces Spec Kit entirely.

**Pros:**

- Single source of truth

**Cons:**

- Massive scope and timeline

- Abandons existing Spec Kit users

- Hostile to the ecosystem

- Not viable

### Option D: Merge into Spec Kit

conventional-agents becomes a submodule or component of Spec Kit.

**Pros:**

- Single integrated system

**Cons:**

- conventional-agents loses independence and becomes tied to Spec Kit's release cycle

- Cannot be used standalone

- Adds bloat to Spec Kit

- Not aligned with stated goals of composability

## Decision Outcome

Chosen option: **Option B (Stay Strictly Adjacent – Standards Only, Never Orchestration)**.

Rationale:

- Clear scope boundaries minimize maintenance burden and reduce risk.

- conventional-agents's value proposition is clarity and standards, not orchestration.

- Spec Kit is the established solution for workflow orchestration; conventional-agents should complement, not compete.

- This approach allows conventional-agents to remain lightweight, focused, and valuable even in projects that don't use Spec Kit.

- A clear boundary reduces integration friction and confusion.

### Scope Definition

**conventional-agents INCLUDES:**

- ✅ Quality gates and testing standards (e.g., coverage, linting, type safety)

- ✅ Role contracts and responsibility boundaries (Implementer, Reviewer, Analyzer)

- ✅ Integration precedence rules (AGENTS.md, tool-specific files)

- ✅ Evidence-based guidelines (bash, Python, documentation practices)

- ✅ Reusable templates (ADRs, specifications, code reviews)

- ✅ Definition of "done" criteria and acceptance checks

- ✅ References and integration points for Spec Kit workflows

**conventional-agents DOES NOT INCLUDE (and never will):**

- ❌ Workflow orchestration (multi-step task sequencing)

- ❌ Modifications to .specify/ directory or structure

- ❌ Coordination of which agents run in which order

- ❌ State machines or decision logic for workflow execution

- ❌ Integration with Spec Kit internals (only via public contracts)

- ❌ Dependencies on Spec Kit being present (standalone value)

### Integration with Spec Kit

**Integration point (read-only):**

- Spec Kit workflows may reference conventional-agents standards and role contracts.

- Spec Kit's `.specify/memory/constitution.md` can include references to `vendor/conventional-agents/` paths.

- Example: "After Implementer completes, check against `vendor/conventional-agents/roles/implementer.md` quality gates."

**Spec Kit does NOT depend on conventional-agents:**

- Spec Kit remains fully functional if conventional-agents is not present.

- conventional-agents remains fully functional if Spec Kit is not present.

- Both are optional dependencies that enhance each other if used together.

**No internal coupling:**

- conventional-agents contains zero imports, references, or dependencies on Spec Kit code or .specify/ internals.

- If Spec Kit changes, conventional-agents does not break.

### Non-Goals Documentation

**Non-goals section (to be added to README.md or ARC42 Section 2):**

conventional-agents is NOT:

- A workflow orchestration engine (that's Spec Kit)

- A task scheduler or job runner

- A multi-step coordination framework

- A replacement for Spec Kit or any other workflow tool

- A system that reads or modifies .specify/ directory

conventional-agents is:

- A quality and standards foundation layer

- A set of reusable templates and guidelines

- An integration bridge that helps teams use multiple tools together

- Standalone and usable without Spec Kit (though complementary if both are used)

## Consequences

### Positive

- conventional-agents remains focused and maintainable.

- Clear boundaries prevent scope creep and feature bloat.

- Spec Kit users can confidently adopt conventional-agents without redundancy.

- conventional-agents can be used in projects that don't use Spec Kit.

- Integration between the two projects is predictable and non-invasive.

- Risk of coupling and maintenance hell is minimized.

- Team expertise requirements are clear and achievable.

### Negative

- Some complex workflows may require separate setup in both conventional-agents and Spec Kit (mitigated by example integration docs).

- Users must understand two separate systems if they use both (mitigated by clear documentation of roles and integration points).

- conventional-agents cannot solve workflow orchestration problems directly (but that's not its mission).

**Mitigations:**

- INTEGRATION.md includes examples of how conventional-agents and Spec Kit work together.

- README.md clearly states "conventional-agents is a standards layer, not a workflow engine."

- Cross-references in both projects' docs make the relationship explicit.

### Neutral

- This decision does not constrain Spec Kit's development or scope.

- This decision does not require any changes to existing Spec Kit systems.

- Teams using only conventional-agents (without Spec Kit) are unaffected.

## Validation

We will consider this decision successful if:

1. **Non-Goals Clarity:**

   - "Non-goals" section exists in README.md or ARC42 and references this ADR.

   - The section explicitly lists what conventional-agents does NOT do (workflow orchestration, .specify/ modifications).

2. **Zero Scope Creep:**

   - No workflow orchestration code appears in conventional-agents.

   - No code that reads or modifies .specify/ exists.

   - No dependency on Spec Kit internals is introduced.

3. **Integration Documentation:**

   - INTEGRATION.md includes at least one worked example of conventional-agents + Spec Kit working together.

   - Example shows how role contracts from conventional-agents are referenced in a Spec Kit workflow.

   - No circular dependencies or tight coupling is present.

4. **Standalone Functionality:**

   - conventional-agents can be cloned and used in a project with no Spec Kit present.

   - All guidelines, roles, and templates are self-contained and functional.

**Measurable Signals:**

- Grep for `.specify` in conventional-agents codebase returns zero matches (no .specify/ dependencies).

- No imports or require statements that reference Spec Kit modules.

- Documentation clearly separates "what conventional-agents does" from "what Spec Kit does."

**Review Checkpoints:**

- At PR review: any PR adding .specify/ references or workflow orchestration code is rejected with a link to this ADR.

- Quarterly: confirm no scope creep has occurred; update Non-Goals section if needed.

- When Spec Kit changes: verify no conventional-agents code broke (zero coupling expected).
