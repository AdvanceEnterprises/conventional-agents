# ADR-0004: AGENTS.md as Canonical Integration Surface

## Status

- Accepted

## Context and Problem Statement

Multiple tools and runtimes (Claude Code, Aider, Cursor, Codex) need a consistent, discoverable entry point for agent instructions in host repositories. Without a canonical anchor file, different tools may read different files or formats, leading to:

- **Anchor fragmentation risk (HIGH):** Each tool invents its own root file (e.g., Claude reads CLAUDE.md, Cursor reads .cursorrules, Aider reads .aider.conf).

- **Instruction conflicts:** Host repos end up maintaining multiple versions of the same guidance, with no clear precedence.

- **Integration chaos:** New tools cannot reliably discover instructions without tool-specific file scanning logic.

The core problem: How do we define a single, tool-neutral entry point that all agents understand, while still supporting tool-specific optimizations?

## Decision Drivers

- **Consistency:** All tools must respect the same source of truth for instruction precedence.

- **Discoverability:** New tools can find instructions without hard-coded file scanning.

- **Flexibility:** Tool-specific configs can still exist but must defer to canonical precedence.

- **Submodule compatibility:** The anchor must work in both submodule and copy-in deployments.

- **Simplicity:** Minimal setup burden for host repo maintainers.

## Considered Options

### Option A: No Canonical Anchor (Each Tool Uses Its Own File)

Tools independently discover their preferred files.

**Pros:**

- No coordination needed

- Each tool optimized for its native config format

**Cons:**

- HIGH risk of instruction fragmentation and conflicts

- Host repos must maintain N different files with overlapping content

- New tools require new integration work

- No precedence mechanism exists

- Difficult to audit which instructions are actually active

### Option B: AGENTS.md as Canonical with Strict Precedence Hierarchy (CHOSEN)

AGENTS.md acts as the primary integration surface. All tools reference it first. If a tool-specific file exists, it may only extend AGENTS.md, not override it. A clear precedence hierarchy prevents conflicts.

**Pros:**

- Single source of truth for all tools

- Clear, auditable precedence prevents conflicts

- New tools can integrate with a standard reference

- Supports both submodule and copy-in patterns

- Host repos maintain one authoritative instruction file

- Tool-specific optimizations can coexist without risk

**Cons:**

- Requires tool ecosystem to adopt AGENTS.md convention

- Precedence hierarchy must be documented and enforced

- Setup requires explaining precedence to contributors

### Option C: Tool-Specific Files as Peers with No Precedence

Multiple root files (AGENTS.md, CLAUDE.md, .cursorrules, etc.) exist as independent peers with no defined hierarchy.

**Pros:**

- Each tool gets native format support

- Minimal constraint on tool internals

**Cons:**

- Unresolvable conflicts when files contradict

- No way to determine which instructions apply

- Fragmentation guaranteed

- Maintenance nightmare for host repos

- Cannot ensure universal gates are respected

## Decision Outcome

Chosen option: **Option B (AGENTS.md as Canonical with Strict Precedence Hierarchy)**.

Rationale:

- Instruction fragmentation is a known risk in the agent tooling landscape.

- A single canonical entry point with clear precedence prevents conflicts and audits.

- This approach allows tool-specific optimizations (CLAUDE.md, .cursorrules) to coexist without risk, as long as they defer to AGENTS.md.

- AGENTS.md is language-neutral and supported as a convention by multiple tools.

### File System Contract (Stable Paths)

**Canonical anchor location:**

- `./AGENTS.md` (root of host repository)

**Precedence Hierarchy (binding order):**

1. **Host repo AGENTS.md** (highest authority)

   - Project-specific constraints and decisions

   - Can override 3-5 and strengthen 2

2. **Universal gates:** `vendor/conventional-agents/roles/ROLE_CONTRACT.md`

   - Cannot be weakened or bypassed

   - Applies to all projects and tools

3. **Role-specific contracts:** `vendor/conventional-agents/roles/{role}.md`

   - Role-specific behavior, guardrails, quality gates

   - Can strengthen 4-5, defer to 1-2

4. **Guidelines:** `vendor/conventional-agents/guidelines/`

   - Evidence-based practices, checklists, testing standards

   - Can be tailored by 1 and 3

5. **Tool-specific configs** (lowest authority)

   - `CLAUDE.md`, `.cursorrules`, `.aider.conf`, etc.

   - Must defer to 1-4

**Principle:** If instructions conflict, the *lowest-numbered* (highest-priority) source wins. Strengthening is allowed (e.g., project adds stricter coverage); weakening universal gates is not allowed.

## Consequences

### Positive

- All tools reference a common entry point, eliminating fragmentation.

- Clear precedence rules make instruction conflicts resolvable and auditable.

- New tools can integrate without duplicating guidance or inventing new files.

- Host repos maintain a single source of truth instead of N parallel versions.

- Strengthening guidelines at the project level is supported explicitly.

- Universal guardrails cannot be bypassed by tool-specific optimizations.

### Negative

- Requires tooling ecosystem to recognize and respect AGENTS.md convention.

- The precedence hierarchy adds complexity for host repo maintainers (mitigated by clear documentation and examples).

- Initial setup requires explaining precedence to contributors (mitigated by a concise INTEGRATION.md and onboarding docs).

- Tools that only read tool-specific files will need upstream updates to support AGENTS.md discovery.

**Mitigations:**

- INTEGRATION.md provides concise, example-driven documentation of precedence.

- AGENTS.md stubs can be minimal (5-10 lines) to keep setup friction low.

- Clear onboarding text in README.md explains when and why tool-specific files matter.

### Neutral

- This decision does not require host repos to abandon CLAUDE.md, .cursorrules, or other tool-specific files.

- Tool-specific files can coexist as long as they defer to AGENTS.md guidance.

- The precedence hierarchy is a policy, not a technical constraint; enforcement relies on tool discipline and code review.

## Validation

We will consider this decision successful if:

1. **Integration Simplicity:**

   - A new host repo can integrate conventional-agents with fewer than 5 lines in AGENTS.md.

   - Setup time (reading docs, writing minimal AGENTS.md) is under 10 minutes.

2. **Conflict Resolution:**

   - When both AGENTS.md and tool-specific files exist, there are zero observed conflicts (verified by code review).

   - Maintainers can explain instruction precedence in under 2 minutes.

3. **Tool Adoption:**

   - At least 3 different tools (e.g., Claude Code, Aider, Cursor) successfully use the same AGENTS.md without tool-specific patches.

   - New tools can integrate with conventional-agents by reading AGENTS.md alone.

4. **Documentation Quality:**

   - INTEGRATION.md includes at least 2 worked examples of precedence resolution.

   - A decision matrix exists showing when each source applies.

**Measurable Signals:**

- Submodule integrations include AGENTS.md as a peer to .gitmodules.

- No merge conflicts or precedence disputes arise during PR reviews.

- When precedence questions occur, they are resolved by referencing INTEGRATION.md or ADR-0004.

**Review Checkpoints:**

- After first 3 integrations: confirm setup simplicity and tool adoption.

- Quarterly: confirm no fragmentation has occurred, precedence rules are still clear, and new tools integrate smoothly.
