# ADR-0009: Feature Specification Template Selection

## Status

- Accepted

## Context and Problem Statement

The conventional-agents repository needs a standardized template for feature specifications that contributors can use to plan and document features. A feature specification template should:

- Support AI-assisted development (explicit parsing hints, structured test generation).

- Enable automated test creation from success criteria.

- Work across multiple agent runtimes (Claude, Codex, Aider, Cursor, etc.).

- Cover operational concerns (security, observability, rollout, dependencies).

- Be simple enough to not require extensive section completion for small features.

- Be compatible with MIT-style licensing or more permissive licenses.

Currently, conventional-agents has a working feature-spec.md template (`templates/core/feature-spec.md`, ~77 lines) with AI optimization (PARSING_HINTS) and Given-When-Then success criteria format. However, no formal decision has been made whether to keep this template, adopt an open-source alternative, or create a hybrid approach.

**The core problem:** Should we keep the current feature-spec.md template, adopt GitHub Spec Kit's template structure, or explore another approach? This decision affects how contributors plan and document features in the conventional-agents ecosystem.

## Decision Drivers

- **AI-agent compatibility:** Template should work well with AI-assisted development and include explicit parsing hints.

- **Test generation:** Should support automated test creation (Given-When-Then format preferred).

- **Licensing:** Must be MIT-compatible or more permissive; no GPL or commercial restrictions.

- **Tool neutrality:** Should work across multiple agent runtimes without tool-specific lock-in.

- **Completeness:** Should cover operational concerns (security, observability, rollout) without being heavyweight.

- **Simplicity:** Should not force unnecessary sections; contributors should skip sections that don't apply.

- **Alignment with ADR-0007:** Must not compete with Spec Kit's workflow orchestration role (adjacent-to, not competing-with).

- **Adoption precedent:** Should build on practices proven in conventional-agents (role contracts, PARSING_HINTS).

## Considered Options

### Option A: Keep Current Template (Status Quo)

Continue using the existing `templates/core/feature-spec.md` template as the authoritative feature spec format.

**Current template characteristics:**

- YAML frontmatter with status workflow (Draft → Approved → Implemented → Deprecated)

- PARSING_HINTS block for AI agents (explicit parsing instructions, test generation guidance)

- Comprehensive sections: Goals, Non-Goals, Users/Stakeholders, Interfaces, Success Criteria, Edge Cases, Out of Scope, Dependencies, Rollout, Observability, Security, Open Questions

- Given-When-Then format for success criteria (test-generation ready)

- ~77 lines, medium complexity

- Already documented and in use (no migration needed)

**Pros:**

- Already implemented and working in conventional-agents.

- AI-optimized with PARSING_HINTS block for explicit agent guidance.

- Test-generation ready with Given-When-Then format in Success Criteria section.

- Covers operational concerns (security, observability, rollout, dependencies).

- No licensing concerns; fully owned by project.

- No migration effort required; template already proven in use.

- Aligned with conventional-agents philosophy (explicit, checkable, evidence-based).

- Can be extended incrementally without breaking changes.

**Cons:**

- Not backed by a major company or project (lower community trust).

- Limited external adoption compared to alternatives.

- No external tooling ecosystem (agents must implement parsing from scratch).

- May miss best practices from larger, battle-tested projects.

- Requires community validation and peer review to build confidence.

### Option B: Adopt GitHub Spec Kit

Replace current template with GitHub Spec Kit's `.specify/` directory structure and five-step workflow (Constitution → Specify → Plan → Tasks → Implement).

**Spec Kit characteristics (MIT, 2025):**

- Purpose-built for AI-assisted development.

- Multi-agent compatible (Claude, Gemini, Copilot, Cursor, etc.).

- Five-step workflow with `.specify/` directory structure.

- 65.7k GitHub stars; strong community adoption.

- Modern (2025) and actively maintained.

- Includes task breakdown and orchestration methodology.

- Constitution.md concept for project-level constraints.

**Pros:**

- Purpose-built for AI-assisted development and development workflow orchestration.

- Strong community adoption (65.7k stars, active ecosystem).

- Multi-agent compatible and modern.

- Includes task breakdown methodology (Plan → Tasks → Implement).

- Includes constitution pattern for project-level governance.

- Active maintenance and growing ecosystem.

**Cons:**

- **Conflicts with ADR-0007:** Spec Kit is a workflow orchestration framework; adopting it moves conventional-agents into workflow orchestration, which ADR-0007 explicitly forbids. conventional-agents is meant to be a standards and quality layer, not a competing workflow engine.

- Major migration effort required; existing feature-spec.md would be replaced.

- More complex workflow (five steps) than single-document approach; may be overkill for small features.

- Introduces `.specify/` directory structure that requires workflow tooling.

- Couples conventional-agents to Spec Kit's internals and release cycle.

- Creates confusion: Spec Kit provides orchestration; conventional-agents should provide standards.

- Risk of feature duplication (both projects document workflows, decision patterns).

- Requires adoption of Spec Kit in host repositories (not all teams use Spec Kit).

### Option C: Hybrid Approach – Current Template + Spec Kit Concepts

Keep current feature-spec.md while adopting specific concepts from Spec Kit (e.g., Constitution.md for project-level constraints, Appetite section from Shape Up).

**Pros:**

- Preserves existing work and avoids migration.

- Adopts best practices from Spec Kit without adopting entire framework.

- Maintains simplicity for small features.

- Allows gradual adoption of new concepts (versioned templates).

**Cons:**

- Creates multiple formats to maintain (feature-spec.md vs. constitution.md vs. future variants).

- Increases cognitive load for contributors (which template to use? when?).

- More documentation burden to explain when to use which format.

- Risk of feature creep as new concepts are added incrementally.

- May end up with a Frankenstein template that borrows from many sources without coherent philosophy.

### Option D: Create New Custom Template

Design a new template combining best practices from multiple sources: current template's AI optimization, HashiCorp's two-tier approach (full RFC + mini RFC), Shape Up's Appetite and Rabbit Holes, Google's trade-offs emphasis.

**Pros:**

- Best-of-breed approach tailored specifically to conventional-agents needs.

- Can optimize specifically for AI + testing.

- Full control over design and evolution.

**Cons:**

- Significant design and validation effort required.

- Not backed by a major project; custom solutions carry higher risk.

- May reinvent the wheel and miss existing best practices.

- Requires community consensus and peer review.

- Higher maintenance burden.

- No external tooling ecosystem support.

## Decision Outcome

Chosen option: **Option A (Keep Current Template as v1.0)**.

Rationale:

1. **Alignment with ADR-0007 (Critical):** Adopting GitHub Spec Kit (Option B) would risk violating ADR-0007's clear boundary: "conventional-agents provides standards and quality gates, never workflow orchestration." Spec Kit is a workflow orchestration framework. conventional-agents should remain complementary, not competitive. Keeping the current template preserves this distinction.

2. **AI Optimization Advantage:** Current template is already optimized for AI agents with PARSING_HINTS block and explicit parsing instructions. This is a core strength that differentiates conventional-agents from generic templates.

3. **Test Generation Ready:** Given-When-Then format in Success Criteria enables direct, automated test generation. This aligns with conventional-agents's emphasis on quality and testing.

4. **Zero Migration Cost:** Keeping the current template avoids disrupting existing users and allows focus on other gaps (roles/, packs/, integrations/).

5. **Simplicity:** Current template is simpler than Spec Kit's five-step workflow, appropriate for a standards repository. Contributors can skip optional sections.

6. **Proven in Use:** Template is already documented and used; it has minimal validation overhead.

7. **Versioned Evolution:** Establish current template as v1.0. Future improvements create new versions (v2.0, v3.0) with clear migration paths and no breaking changes to existing specs.

### Complementary Relationship with Spec Kit

This decision positions GitHub Spec Kit as complementary, not competing:

- **conventional-agents:** Provides quality standards, role contracts, and reusable templates (feature-spec.md, ADRs, etc.).

- **GitHub Spec Kit:** Provides workflow orchestration, multi-step coordination, and task breakdown.

- **MADR:** Provides decision-record format for architectural decisions (already used in conventional-agents).

**Integration pattern:**

- Projects can use both: Spec Kit for orchestration (Constitution → Specify → Plan → Tasks → Implement), conventional-agents feature-spec.md for individual feature documentation.

- Spec Kit's "Specify" phase can reference conventional-agents templates and standards.

- Both remain standalone; neither depends on the other.

### Template Versioning Strategy

To enable future evolution without breaking existing specs:

**Version numbering:**

- **Major version (v2.0, v3.0, etc.):** Breaking changes only. Examples: removed sections, changed frontmatter fields, different structure. Requires new template file (feature-spec-v2.0.md).

- **Minor version (v1.1, v1.2, etc.):** Non-breaking additions only. Examples: new optional sections, expanded examples, clarified guidance. Use same template file or minor versioning in YAML.

**File management:**

- Current template: `templates/core/feature-spec.md`

- Becomes: `templates/core/feature-spec-v1.0.md` (explicitly versioned)

- Create symlink or copy: `templates/core/feature-spec.md` → points to latest (v1.0)

- Add `template_version: "1.0"` field to frontmatter for version tracking in specs.

**Adoption:**

- Keep `feature-spec.md` as the canonical reference (latest version).

- Versioned templates (v1.0, v2.0) serve as historical references and migration guides.

- Breaking changes trigger new major version; minor improvements don't require migration.

## Consequences

### Positive

- conventional-agents remains focused on standards and quality, complementary to Spec Kit.

- Current template is proven, documented, and requires no migration effort.

- AI optimization (PARSING_HINTS) is retained and can be enhanced over time.

- Test generation capability is preserved and encourages quality.

- Clear boundary with Spec Kit reduces scope creep risk (per ADR-0007).

- Versioning strategy allows feature evolution without breaking existing specs.

- Flexibility: contributors can skip optional sections for small features.

- No dependency on external projects (Spec Kit, GitHub, etc.).

### Negative

- Current template is not backed by a major project; may face skepticism from teams familiar with alternatives.

- No external tooling ecosystem; agents must implement PARSING_HINTS parsing from scratch.

- Requires community validation and peer review to build confidence (not a known standard like MADR).

- May miss some best practices from larger projects that only become apparent over time.

**Mitigations:**

- Document the decision and rationale in this ADR (transparent decision-making).

- Include references and validation strategies in Success Criteria (see Validation section).

- Encourage feedback and improvements via GitHub issues; treat template as evolving, not fixed.

- Monitor Spec Kit and other alternatives; revisit this decision annually to ensure it still holds.

### Neutral

- This decision does not constrain Spec Kit's development or prevent host repos from using Spec Kit.

- Teams can use both Spec Kit (for orchestration) and conventional-agents templates (for specs) without conflict.

- Teams using only conventional-agents (without Spec Kit) remain unaffected.

- MADR remains the decision-record template; feature-spec.md is for feature planning only.

## Validation

We will consider this decision successful if:

1. **Template Adoption:**

   - At least 3 features are documented using feature-spec-v1.0.md template successfully.

   - Template sections are completed appropriately (contributors can skip non-applicable sections).

   - No blocking issues or requests to replace the template.

2. **AI Optimization:**

   - PARSING_HINTS block is parsed correctly by at least 2 different AI agents (Claude, Cursor).

   - Success Criteria (Given-When-Then format) enable test generation without modification.

   - Agents can generate accurate tests from Success Criteria.

3. **Integration with Spec Kit (Complementary):**

   - INTEGRATION.md includes documentation of how conventional-agents templates and Spec Kit work together.

   - No conflicts or redundancy reported when Spec Kit is used with conventional-agents.

   - Teams using both tools report no confusion about responsibilities.

4. **Versioning Setup:**

   - `templates/core/feature-spec-v1.0.md` exists with explicit version in frontmatter.

   - `templates/core/feature-spec.md` is a symlink or copy pointing to v1.0.

   - Template versioning strategy is documented in templates/core/README.md or ARC42 Section 4.

5. **No Scope Creep:**

   - No workflow orchestration code appears in conventional-agents as a result of this decision.

   - ADR-0007 boundary remains intact (standards only, never orchestration).

   - No dependency on Spec Kit internals introduced.

**Measurable Signals:**

- Grep for feature-spec.md in docs/ and roles/ returns clear, version-aware references.

- At least 1 GitHub issue or discussion mentions feature-spec.md being useful and well-documented.

- Zero bugs or gaps reported in template sections for first 3 features documented.

- ARC42 Section 9 updated to list ADR-0009 and versioning strategy.

**Review Checkpoints:**

- At first feature-spec.md PR: confirm template works and test generation is viable.

- After 3 features: gather feedback and assess need for template improvements.

- Annually: review Spec Kit, other alternatives, and this decision to ensure it still holds.
