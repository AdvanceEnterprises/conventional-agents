# ADR-0000: Use MADR and arc42 template as documentation origins

## Status
- Accepted

## Context and Problem Statement
We need consistent, durable documentation standards for:
- Architecture documentation (structure and sections)
- Architecture decision records (format and lifecycle)

Constraints:
- Documentation must remain readable as plain markdown.
- Documentation must be tool-agnostic and work across different AI coding assistants.
- The repository should be submodule-friendly and allow vendoring upstream templates for traceability.
- We want stable origin references so that future contributors can understand the provenance of our structure and ADR format.

## Decision Drivers
- Consistency across decisions and architecture docs
- Tool neutrality (plain markdown)
- Ease of adoption (clear templates)
- Maintainability (low drift, predictable structure)
- Traceability (upstream provenance)
- Submodule friendliness (vendor the upstream sources without rewriting them)
- Longevity (well-known, community-maintained approaches)

## Considered Options
### Option A: Invent a custom ADR and architecture documentation format
Short description.
- Pros
  - Full control
- Cons
  - Reinvents existing work
  - Higher risk of inconsistency and drift
  - Harder onboarding for new contributors

### Option B: Use MADR for ADRs and arc42 for architecture structure (vendor upstream templates)
Short description.
- Pros
  - Proven patterns with broad community familiarity
  - Consistent ADR structure (MADR) and consistent architecture structure (arc42)
  - Upstream provenance is explicit
- Cons
  - Some process overhead (keeping templates pinned and referenced correctly)
  - arc42 and MADR are separate artifacts and must be wired together intentionally

### Option C: Use arc42 only, and record decisions informally inside arc42 section 9
Short description.
- Pros
  - Fewer files
- Cons
  - Decisions become harder to track, diff, and evolve
  - Harder to manage status lifecycle (proposed, accepted, superseded, deprecated)

## Decision Outcome
Chosen option: Option B.

We will:
- Use MADR as the ADR template and lifecycle format.
- Use the arc42 template as the origin point for the architecture documentation structure.
- Vendor both as git submodules to preserve provenance and reduce template drift.

### Implementation notes
- MADR is vendored as a git submodule and pinned to the v4.0.0 release tag:
  - https://github.com/adr/madr/releases/tag/4.0.0
- arc42 template is vendored as a git submodule:
  - https://github.com/arc42/arc42-template.git
- Project-specific architecture documentation lives in:
  - docs/arc42.md
- Project ADRs live in:
  - docs/adr/ADR-XXXX.md
- The repository uses MADR-style ADR front matter compatible with parsing by coding agents.

## Consequences
### Positive
- Clear, predictable structure for architecture docs and decisions.
- ADRs become easy to review, diff, and evolve over time.
- Contributors can trace the origin of the templates and conventions.
- The system remains plain markdown and tool-agnostic.

### Negative
- Submodules add operational overhead (initialization, updating, pinning).
- arc42 template updates require deliberate decisions about when to adopt changes.
- Contributors must learn where the canonical templates live versus where project docs live.

### Neutral
- We will keep the upstream templates vendored, but we will not treat them as the project documentation itself.
- The project arc42 document and ADRs can diverge from upstream templates as needed, but the upstream sources remain the reference origin.

## Validation
We will consider this decision successful if:
- New contributors can create a compliant ADR in under 10 minutes using the vendored MADR template.
- Architecture documentation remains consistent and navigable across releases.
- The arc42 document links to the ADR index and the most important accepted ADRs.
- Automated or manual checks confirm that ADRs use the expected front matter fields (type, id, status, decision_scope, reversible).

Review checkpoints:
- After 5 ADRs: verify the workflow is smooth and the templates are working.
- Quarterly: verify submodule pins are still intentional and documented.
