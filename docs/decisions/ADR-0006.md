# ADR-0006: Role-as-Skill-Card Format

## Status

- Accepted

## Context and Problem Statement

The conventional-agents repository needs to define role contracts that specify what responsibilities, guardrails, and quality gates apply to different agent roles (e.g., Analyzer, Implementer, Reviewer). Currently, `roles/ROLE_CONTRACT.md` is empty, and the format for role definitions is undocumented, despite being sketched in ARC42.md Section 5.3.

Without a consistent, structured format, role contracts risk being:

- **Vague or prose-heavy:** Difficult for agents to parse or validate.

- **Inconsistent:** Different roles defined in different styles, making comparisons hard.

- **Unenforceable:** Without clear inputs, outputs, and gates, it's difficult to build tooling or checklists.

- **Disconnected from implementation:** Guidelines and skill definitions use different terminology than role contracts.

The core problem: How do we define roles in a way that is both human-readable and machine-parseable, with explicit gates and acceptance criteria?

## Decision Drivers

- **Clarity:** Role boundaries, responsibilities, and constraints must be immediately clear.

- **Consistency:** All roles should be defined in the same format and structure.

- **Enforceability:** Roles should include acceptance checks that tools or code reviewers can validate.

- **Parsability:** Tools should be able to extract inputs, outputs, and gates programmatically.

- **Alignment with guidelines:** Role format should align with existing skill and guideline documentation.

## Considered Options

### Option A: Traditional Prose Definitions

Define roles as narrative markdown sections with no fixed structure (e.g., "Role: Implementer – This role is responsible for…").

**Pros:**

- Familiar to most contributors

- No forced structure, allows flexibility

- Easy to add contextual explanation

**Cons:**

- Hard to parse programmatically

- Inconsistent application across roles

- Difficult to extract acceptance criteria

- Tools cannot reliably validate compliance

- Vague boundaries between role input and output

### Option B: Skill-Card Format (CHOSEN)

Define roles using a structured skill-card format with explicit Purpose, Inputs, Outputs, Guardrails, Quality Gates, and Acceptance Checks sections.

**Pros:**

- Clear, consistent structure across all roles

- Inputs and outputs are explicit and discoverable

- Guardrails are separated from guidelines

- Quality gates are measurable and enforceable

- Agents and tools can parse sections programmatically

- Aligns with existing skill definitions in ARC42

- Easy to extend with tool-specific sections

**Cons:**

- Stricter format may feel constraining for some contexts

- Requires discipline to fill out correctly

- Schema changes would require updating all role files

### Option C: YAML-Based Format

Define roles as YAML files with structured metadata (inputs, outputs, gates as arrays/objects).

**Pros:**

- Machine-readable and language-parseable

- Supports complex constraints (arrays, nested objects)

- Integrates well with automation

**Cons:**

- Less human-readable in raw form

- Requires YAML parsing tooling

- Harder to mix with prose explanation

- Not aligned with existing markdown-first approach

- More friction for manual editing and reviews

### Option D: Separate Formats for Roles vs. Skills

Use skill-card format for skills, traditional prose for roles (or vice versa).

**Pros:**

- Optimizes each type for its use case

**Cons:**

- Fragmentation and inconsistency

- Contributors must learn multiple formats

- Roles and skills are often tightly coupled; inconsistent format creates confusion

- Increases cognitive load

## Decision Outcome

Chosen option: **Option B (Skill-Card Format)**.

Rationale:

- ARC42.md Section 5.3 already describes the skill-card format, indicating internal consensus on its usefulness.

- A consistent structure makes role contracts explicit and enforceable.

- Skill-card format is more structured than prose (good for parsing) but more readable than YAML (good for humans).

- This approach aligns roles and skills, reducing cognitive load.

### Template Structure

**Skill-card format for roles:**

```markdown
# Role: [Role Name]

## Purpose
[1-2 sentences describing the role's primary responsibility and scope.]

## Inputs Required
- [What information, code, or context must the agent receive?]
- [What preconditions must be met?]
- [What files or systems must be accessible?]

## Outputs Expected
- [What deliverable(s) does the agent produce?]
- [What format or quality standard applies?]
- [What stakeholder receives the output?]

## Guardrails (Boundaries)
- [What must the agent NOT do?]
- [What decisions are outside this role's scope?]
- [What dependencies or escalation paths apply?]

## Quality Gates
- [What measurable standards apply? (e.g., test coverage, documentation, no security violations)]
- [What review checkpoints must pass?]
- [What tools or manual checks validate compliance?]

## Acceptance Checks
- [Checklist of verifiable outcomes]
- [Example: "All tests pass with 80%+ coverage"]
- [Example: "Security gate: no hardcoded secrets, no shell injection risks"]

## Related Guidelines
- [Links to applicable guidelines, tools, and documentation]
```

### Example: Implementer role (filled template)

```markdown
# Role: Implementer

## Purpose
The Implementer writes code that solves the problem defined in a spec or task. The role is responsible for code quality, testing, and adherence to project guidelines.

## Inputs Required
- Specification or task description (from Analyzer or Reviewer)
- Project context (AGENTS.md, codebase structure, current tests)
- Access to version control and project dependencies

## Outputs Expected
- Implementation code in the specified language/framework
- Unit tests with 80%+ coverage
- Passing CI/CD checks (linting, type checking, tests)

## Guardrails (Boundaries)
- Do NOT modify architecture without a decision record (ADR).
- Do NOT skip tests or reduce coverage below project minimum.
- Do NOT make breaking changes without explicit approval.
- Do NOT deploy or merge without code review.

## Quality Gates
- All tests pass
- Coverage ≥ 80% (or project-specific minimum)
- No linting or type errors
- Code review approval required

## Acceptance Checks
- [ ] Specified feature is implemented
- [ ] Tests pass locally and in CI
- [ ] Coverage meets threshold
- [ ] Code review approved
- [ ] Related documentation updated

## Related Guidelines
- vendor/conventional-agents/guidelines/tests.md
- vendor/conventional-agents/guidelines/commit-and-pr.md
- [project-specific] AGENTS.md Quality Gates section
```

### File System Contract (Stable Paths)

**Universal role contract:**

- `roles/ROLE_CONTRACT.md` – Universal gates and shared guardrails (applies to all roles)

**Role-specific contracts:**

- `roles/<role-name>.md` – One file per role (e.g., `roles/implementer.md`, `roles/reviewer.md`, `roles/analyzer.md`)

**Stability constraint:**

- The skill-card format (Purpose, Inputs, Outputs, etc.) must be documented in this ADR or in a canonical schema.

- If the format changes, it is a breaking change and must be introduced via a new ADR.

## Consequences

### Positive

- Roles are defined consistently and unambiguously.

- Inputs and outputs are explicit, making it easy to verify that a role is ready to act.

- Quality gates are measurable, enabling both automated checks and manual code review.

- Agents can parse sections programmatically to extract constraints.

- Role definitions serve as both documentation and acceptance criteria.

- Easy to extend with tool-specific sections or fields without losing structure.

- Aligns with ARC42 Section 5.3 design, reducing revision risk.

### Negative

- Structured format requires discipline; poorly filled templates are unhelpful (mitigated by examples and review).

- Initial effort to define universal gates and role-specific contracts.

- Format is stricter than prose, which some may find constraining.

**Mitigations:**

- Provide filled templates for common roles (Implementer, Reviewer, Analyzer).

- Code review checklist ensures templates are used correctly.

- Guidance in ADR explains each section's purpose and what to include.

### Neutral

- This decision does not constrain which roles exist or how many roles are defined.

- Projects can define additional roles beyond the universal set if needed.

- Roles can reference external guidelines without including full content.

## Validation

We will consider this decision successful if:

1. **Template Completeness:**

   - `roles/ROLE_CONTRACT.md` is populated with universal gates (currently empty).

   - At least 3 role-specific files are created using the skill-card format (e.g., Implementer, Reviewer, Analyzer).

2. **Format Consistency:**

   - All role files follow the template structure (Purpose, Inputs, Outputs, Guardrails, Gates, Checks, Links).

   - Section headings match this ADR exactly (case-sensitive).

   - Agents can reliably parse sections by heading.

3. **Content Alignment:**

   - Each role's inputs clearly indicate what must be provided before the role can act.

   - Each role's outputs match a downstream role's inputs (e.g., Analyzer output → Implementer input).

   - Quality gates reference measurable signals from ARC42 or INTEGRATION.md.

4. **Practical Use:**

   - Code reviewers reference role contracts during PR reviews.

   - Agents cite quality gates when requesting changes.

   - Specification or task handoff includes "assigned role + inputs" in checklist.

**Measurable Signals:**

- All role files include all 7 sections (Purpose through Related Guidelines).

- No role file is shorter than 15 lines or longer than 50 lines (healthy balance of detail).

- Acceptance checks use checkboxes ([ ]) and are specific, not generic.

**Review Checkpoints:**

- After first 3 role definitions: confirm format consistency and usefulness.

- After first 5 code reviews: confirm reviewers can reference and apply role contracts.

- Quarterly: confirm role definitions still map to project practices; update if needed.
