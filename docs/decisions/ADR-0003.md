# ADR-0003: Mirror arc42-template as an upstream-tracking git submodule

## Status

- Accepted

## Context and Problem Statement

We need a durable and maintainable way to use the arc42 markdown template as an architectural origin point for this repo.

We considered two broad approaches:

- Track arc42 upstream via git.

- Consume a packaged artifact (zip) from the upstream repository dist directory and manage updates ourselves.

The core problem:

- We want a reliable way to receive upstream updates with minimal manual work and low risk of drift.

- We also want our repo docs to remain ours (we can copy or adapt templates), while still keeping the upstream source available for reference.

## Decision Drivers

- Update reliability

- Drift control

- Operational simplicity

- Traceability to upstream

- Tool neutrality (plain markdown)

- Submodule friendliness and stable vendor paths

- Low maintenance burden

## Considered Options

### Option A: Vendor only the dist zip

- Regularly download and extract `dist/arc42-template-EN-withhelp-markdown.zip`.

- Store extracted content in-repo and adapt as needed.

- Pros

  - Smaller footprint than the full upstream repo

  - No submodule mechanics for contributors

- Cons

  - Manual or custom automation required to keep current

  - Harder to audit provenance and changes over time

  - Drift risk (local edits mixed with upstream content)

  - Extra decisions required (where to extract, what to overwrite, how to preserve local edits)

### Option B: Add arc42-template as a submodule pinned to a release or commit

- Add the full upstream repo as a submodule and pin to a tag/commit.

- Pros

  - Reproducible and stable

  - Clear provenance and diff against upstream

- Cons

  - Not automatically current

  - Requires intentional updates and periodic review

### Option C: Add arc42-template as a submodule tracking upstream

- Add the full upstream repo as a submodule and update it periodically to track upstream changes.

- Pros

  - Surest path to staying current via git

  - Clear provenance and diffs

  - No zip extraction workflow

  - Upstream reference stays available even if we only copy small parts into our docs

- Cons

  - Updates may introduce churn

  - Requires submodule update discipline

  - Still requires a local policy for how we consume template changes in our own docs

## Decision Outcome

Chosen option: Option C (submodule tracking upstream).

Rationale:

- Git is the most reliable mechanism for tracking upstream updates and understanding what changed.

- The full repo may feel heavy, but it removes the ongoing complexity of zip-based extraction, overwrite rules, and drift management.

- We can keep our repo docs separate and treat the submodule as the upstream reference source.

Decision summary:

- We will add `arc42-template` as a git submodule under `vendor/arc42-template/`.

- We will track upstream changes by updating the submodule pointer periodically.

- We will not treat the submodule contents as the place for our project documentation.

- Our project documentation lives in our own docs tree, and we copy or adapt from the upstream template as needed.

### File system contract (stable paths)

- Upstream template submodule location:

  - `vendor/arc42-template/`

Stability constraints:

- The mount path `vendor/arc42-template/` is intended to be stable.

- If this path changes, treat it as a breaking change to integrations and references.

## Consequences

### Positive

- Upstream updates are easy to pull and audit.

- Provenance is explicit (commit history and diffs).

- No bespoke zip download or extraction workflow needed.

- Keeps the upstream template available as a reference for reviewers and contributors.

### Negative

- The upstream repo footprint is larger than consuming a single zip artifact.

- Updating the submodule may introduce frequent diffs and review noise.

- Contributors must understand submodule basics.

Mitigations:

- Keep the submodule read-only by convention.

- Document the update workflow in `docs/adr/README.md` or `INTEGRATION.md`.

- Prefer a regular cadence for updates rather than constant churn.

### Neutral

- This decision does not force us to mirror the upstream template structure in our own docs.

- We can selectively copy the pieces we need.

Reversal path:

- If upstream tracking creates too much churn, we can switch to pinning to a specific tag or commit (Option B) without changing the submodule mount path.

- If submodules become unacceptable, we can migrate to a zip-based import process (Option A) in a new ADR and retire this one via supersession.

## Validation

We will consider this decision successful if:

- We can update the submodule pointer in a predictable, repeatable way.

- We can audit changes between updates using git diffs.

- Our local documentation remains stable and unaffected unless we intentionally copy changes from the template.

Measurable signals:

- Submodule updates are one small PR or commit that changes only the submodule pointer (plus any intentional local doc changes).

- No local edits occur inside `vendor/arc42-template/` (spot check via git status and review discipline).

Review checkpoints:

- After the first 2 update cycles: confirm churn is manageable.

- Quarterly: confirm the approach still feels lower effort than zip-based imports.
