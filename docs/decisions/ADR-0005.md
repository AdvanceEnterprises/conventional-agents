# ADR-0005: Submodule-First Referencing Strategy

## Status

- Accepted

## Context and Problem Statement

Host repositories need a stable, maintainable way to integrate conventional-agents into their codebase. The challenge is balancing:

- **Update ease:** Consuming conventional-agents should not require complex tooling or manual coordination.

- **Tool compatibility:** Some tools (e.g., Cursor, VS Code extensions) work smoothly with submodules; others prefer files in the root.

- **Drift risk:** Copying files instead of referencing upstream creates maintenance burden and version fragmentation.

- **Deployment flexibility:** Some teams will prefer submodules; others will prefer copying files into their repo.

The core problem: Which deployment pattern should be recommended as the primary approach, and how do we support alternatives without creating confusion or maintenance chaos?

## Decision Drivers

- **Maintainability:** Minimize version fragmentation and drift between conventional-agents and host repos.

- **Flexibility:** Support multiple deployment patterns for different tool ecosystems and team preferences.

- **Clarity:** Recommend one primary pattern with documented alternatives.

- **Stability:** Ensure that regardless of deployment pattern, stable paths remain consistent.

- **Ease of setup:** New integrations should not require complex scripts or tooling.

## Considered Options

### Option A: Submodule Only (Strict)

Only submodule integration is supported. Copy-in and hybrid patterns are not documented or recommended.

**Pros:**

- Clearest single source of truth

- Easiest to maintain and update

- Minimal coordination between repos

**Cons:**

- Excludes tools or teams that cannot use submodules (e.g., some VS Code extension workflows)

- Reduces flexibility and adoption

- Forces users with incompatible tools to fork or duplicate guidance

- HIGH barrier for organizations with root-only tool constraints

### Option B: Copy-In Only

Only copy-in is recommended. Host repos copy files from conventional-agents into their own tree at integration time.

**Pros:**

- Works with all tools

- No submodule machinery needed

**Cons:**

- HIGH drift risk (copies diverge from upstream)

- Updates require manual scanning and cherry-picking

- Easy to accidentally stay on old versions indefinitely

- Version fragmentation across orgs

- Hard to audit which version of guidance is in use

- Maintenance burden grows with each new host repo

### Option C: Submodule-First with Copy-In and Hybrid as Valid Alternatives (CHOSEN)

Recommend submodule as the primary pattern; document copy-in and hybrid patterns as valid alternatives with trade-offs explained.

**Pros:**

- Primary pattern (submodule) is easiest to maintain

- Flexibility supports diverse tool ecosystems

- Clear guidance on when to use each pattern

- Host repos can choose based on their tool constraints

- Hybrid pattern combines benefits of both (submodule + root stubs)

- Easy migration path from copy-in to submodule

**Cons:**

- More documentation and decision-making for integrators

- Multiple patterns increase cognitive load (mitigated by clear checklists)

- Potential for users to pick the wrong pattern without guidance

### Option D: No Recommendation

Leave it to host repos to invent their own deployment pattern.

**Pros:**

- No constraints on teams

**Cons:**

- Fragmentation across organizations

- No guidance for teams new to conventional-agents

- Higher learning curve and setup friction

- Difficult to provide stable path guarantees

## Decision Outcome

Chosen option: **Option C (Submodule-First with Copy-In and Hybrid as Valid Alternatives)**.

Rationale:

- Submodule deployment is the easiest to maintain over time and provides the strongest guarantee of up-to-date guidance.

- Not all tool ecosystems support submodules equally; flexibility is needed.

- The hybrid pattern (submodule + minimal root stubs) offers a good balance: it keeps conventional-agents as the source of truth while allowing tools that only read root files to find their stubs.

- Recommending one primary pattern while documenting alternatives provides clarity without excluding teams with different constraints.

### Deployment Patterns

#### Pattern 1: Submodule (Recommended)

- Add conventional-agents as a git submodule under `vendor/conventional-agents/`.

- Create minimal root-level stubs (AGENTS.md, CLAUDE.md) that reference the submodule.

- Update submodule pointer as needed (e.g., monthly or quarterly).

- Best for: Organizations maintaining multiple repos with consistent standards.

#### Pattern 2: Copy-In (Supported)

- Copy files from conventional-agents into host repo at integration time.

- No ongoing submodule updates.

- Easier for teams unable to use submodules.

- Worst for: Long-term maintenance and version tracking.

- Trade-off: Accept drift risk, document decision in INTEGRATION.md.

#### Pattern 3: Hybrid (Recommended Default)

- Submodule at `vendor/conventional-agents/`.

- Root stubs (AGENTS.md, CLAUDE.md, .cursorrules) that reference submodule content.

- Tools that only read root files can find their preferred stubs immediately.

- Tools aware of submodules can discover and reference canonical content.

- Best for: Mixed tool ecosystems (e.g., VS Code + Claude + Aider).

### File System Contract (Stable Paths)

**Submodule mount path:**

- `vendor/conventional-agents/` (stable across all patterns)

**Root stubs:**

- `AGENTS.md` (optional but recommended)

- `CLAUDE.md` (optional, Claude-specific)

- `.cursorrules` (optional, Cursor-specific)

- `.aider.conf` (optional, Aider-specific)

**Stability constraint:**

- Regardless of which pattern is used, references to `vendor/conventional-agents/` paths must remain stable.

- If this path changes, it is a breaking change for all dependent integrations.

## Consequences

### Positive

- Submodule-first approach minimizes drift and maintenance burden in the long term.

- Flexibility allows adoption across diverse tool ecosystems and team constraints.

- Hybrid pattern provides best-of-both-worlds for mixed environments.

- Clear guidance reduces decision paralysis and integration friction.

- Easy upgrade path: teams can start with copy-in and migrate to submodule later.

- Stable paths ensure that references work in all deployment patterns.

### Negative

- Multiple patterns create more documentation and decision-making for integrators.

- Teams may choose the wrong pattern without guidance (mitigated by clear decision tree in INTEGRATION.md).

- Hybrid pattern requires understanding both submodule mechanics and root-level stub conventions.

- Organizations with strong copy-in practices may resist adopting submodules.

**Mitigations:**

- INTEGRATION.md includes a clear decision tree: "Does your team support submodules? Yes → use Pattern 1. No → use Pattern 2 or 3."

- Example setups for each pattern are provided in packs/ directory.

- Migration guide (copy-in → submodule) is documented.

### Neutral

- This decision does not mandate any particular tool choice or workflow.

- Teams can stay on older versions of conventional-agents if they choose (trade-off: drift risk).

- Tool-specific optimization (CLAUDE.md, .cursorrules) is possible in all patterns.

## Validation

We will consider this decision successful if:

1. **Primary Pattern Adoption:**

   - At least 3 host repos successfully integrate using submodule pattern.

   - Submodule updates happen predictably (monthly or quarterly) with minimal churn.

2. **Alternative Pattern Support:**

   - INTEGRATION.md documents copy-in and hybrid patterns with equal detail to submodule pattern.

   - At least 1 host repo successfully uses copy-in pattern.

   - At least 1 host repo successfully uses hybrid pattern.

3. **Documentation Quality:**

   - Setup instructions exist for all 3 patterns.

   - Pros/cons table explains when to use each pattern.

   - Migration guide (copy-in → submodule) exists and is followed successfully.

4. **Stable Paths Guarantee:**

   - `vendor/conventional-agents/` mount path does not change.

   - All references to vendor paths in docs remain valid across submodule updates.

**Measurable Signals:**

- Host repos using submodule pattern update their pointer without breaking references.

- Copy-in repos document their version and drift explicitly.

- Hybrid repos have both `.gitmodules` entry and root stubs.

**Review Checkpoints:**

- After first 3 integrations: confirm all 3 patterns work as documented.

- Quarterly: confirm stable paths have not broken, update frequency is manageable, and teams are satisfied with their chosen pattern.
