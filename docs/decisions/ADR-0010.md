# ADR-0010: Use Custom Change Plan Template Instead of Open Source Alternative

## Status

Accepted

## Context and Problem Statement

Implementers in conventional-agents need a structured way to plan changes before coding. A change plan should bridge the gap between a feature spec (requirements) and actual implementation, binding the implementer to explicit scope and preventing drift.

Currently, we have a custom change plan template at `templates/core/change-plan.md`. This decision addresses whether to retain this custom template or adopt an existing open source alternative.

The core problem:

- **Scope creep risk (HIGH):** Without an explicit plan contract, implementers may add features or refactoring not in the original spec.

- **Test alignment (MEDIUM):** Implementation must stay synchronized with spec success criteria; a plan should link tests to those criteria.

- **Constraint enforcement (MEDIUM):** Implementers need clear guardrails (what WILL and WILL NOT change); existing templates don't emphasize this.

- **Portability (LOW):** Most open source alternatives are focused on commit messages, changelogs, or process docs, not implementation binding.

## Decision Drivers

- **Binding contract:** The plan must function as a commitment (implementer signs off) to scope and constraints.

- **Test-first alignment:** Plan must link to spec success criteria and drive test cases.

- **Scope enforcement:** Explicit "This change WILL / WILL NOT" sections prevent drift.

- **Implementer clarity:** The template must be actionable by a single implementer, not a process artifact.

- **Spec integration:** The plan must reference feature specs and ADRs as upstream constraints.

- **Minimal friction:** The template should be quick to fill and not onerous.

## Considered Options

### Option A: Keep Custom Template

Use the template at `templates/core/change-plan.md` as-is.

**Pros:**

- Tight alignment with conventional-agents's spec and ADR ecosystem

- Implementer-focused language (role: implementer, not team lead or PM)

- Explicit scope binding (WILL / WILL NOT sections)

- Test-driven (section 3 links to spec success criteria)

- Constraint enforcement (guardrails and non-changes sections)

- Prevents scope creep with declarative sign-off

- Already in use and proven in practice

**Cons:**

- Custom maintenance burden (if template needs changes, we own those updates)

- Non-standard format (not recognized by external tools or teams)

- Requires training/documentation for new contributors

### Option B: Adopt Conventional Commits

Use the Conventional Commits format (feat, fix, refactor, etc.) combined with PR descriptions.

**Pros:**

- Widely recognized and standardized (easy for external contributors)

- Tooling support (commitlint, semver extraction, changelog generation)

- Simple to learn and apply

**Cons:**

- Focused on commit message format, not implementation planning

- No scope binding or contract mechanism

- No test-to-spec alignment support

- Cannot enforce "will NOT change" constraints

- Does not link to feature specs or ADRs

- No explicit sign-off or guardrails

- Designed for communication, not planning

### Option C: Adopt Keep a Changelog Format

Use the Keep a Changelog format for recording planned changes.

**Pros:**

- Standard format with tooling support

- Human-readable and recognizable

**Cons:**

- Designed for user-facing changelog documentation, not implementer planning

- No binding contract or scope enforcement

- No test-to-spec linking

- No guardrails or constraint sections

- Requires interpretation for each change

- Typically filled after implementation, not before

### Option D: Adopt Trunk-Based Development / Git-Flow Checklists

Use process-oriented checklists from Git-flow or trunk-based development literature.

**Pros:**

- Emphasizes process discipline and code review

- Widely documented and recognized

**Cons:**

- Focus is on process (code review, testing, CI/CD gates), not binding to scope

- No explicit linking to specs or success criteria

- Templates are typically generic and don't enforce scope constraints

- Implementer doesn't sign off on scope commitment

- No explicit "will NOT" sections

### Option E: Adopt OAF (Open Architecture Framework) Decision Records

Use OAF-style decision and implementation records.

**Pros:**

- Architecture-focused and rigorous

- Includes decision rationale and alternatives

**Cons:**

- Designed for architectural decisions, not feature implementation

- Too heavy for feature-level changes

- Not test-driven or success-criteria aware

- Does not bind implementer to explicit scope

- Intended for documentation after-the-fact, not planning before

## Decision Outcome

Chosen option: **Option A (Keep Custom Template)**.

Rationale:

Our custom template uniquely addresses the implementer's need for a **binding contract** that:

1. **Links to specs:** Sections 1, 2, and 6 explicitly reference feature specs and ADRs as upstream constraints.

2. **Drives tests:** Section 3 connects to success criteria from the spec, ensuring test coverage aligns with requirements.

3. **Prevents scope creep:** Sections 2 and 9 (WILL / WILL NOT) and the Declaration create explicit boundaries.

4. **Enforces constraints:** Sections 6, 7, and 8 ensure implementer considers guardrails, risks, and validation before starting.

5. **Requires sign-off:** The Declaration section makes scope binding explicit and intentional.

Open source alternatives are designed for different purposes:

- Conventional Commits: commit message format (post-implementation)

- Keep a Changelog: user-facing changelog (post-implementation)

- Git-flow: process discipline (not binding scope)

- OAF: architectural decisions (not feature-level binding)

None of these prevent scope drift or create the binding contract our implementer-driven workflow requires.

### File system contract (stable paths)

- Change plan template location: `templates/core/change-plan.md`

- Stability constraint: The template path and structure are stable integration points for tool loading and documentation.

- If this path or structure changes, treat it as a breaking change to workflows and tool configurations.

## Consequences

### Positive

- Implementers have a clear, binding contract that prevents scope creep.

- Spec-to-test alignment is explicit (success criteria drive test planning).

- Constraint enforcement is built-in (guardrails, non-changes, and sign-off).

- Tool-agnostic (can be used with any implementation tool or CI system).

- Integrates seamlessly with conventional-agents's spec and ADR ecosystem.

- Single source of truth for implementation scope (easier to audit and review).

### Negative

- Custom template requires education and documentation for new contributors.

- Maintenance burden: if template structure needs changes, we must coordinate updates across all change plans.

- Non-standard format; external contributors or other tools may not recognize the structure.

- Possible tool ecosystem misses (commitlint, changelog generators, etc. won't parse the template directly).

Mitigations:

- Document the template with clear instructions in `templates/core/README.md`.

- Include examples of filled-in change plans in the repository.

- Keep the template stable (changes only via new ADRs that supersede this one).

- Treat the custom template as a living document with version tracking via frontmatter (e.g., `version: 1.0`).

### Neutral

- This decision does not preclude using Conventional Commits for commit messages (both can coexist).

- This decision does not preclude generating a changelog from commit messages (separate concern).

- Implementation tooling (CI, testing, code review) is unaffected by this choice.

Reversal path:

- If the custom template becomes unmaintainable or contrib burden grows, we can migrate to a lighter-weight format (e.g., feature branch checklist) in a new ADR.

- Existing change plans would be grandfathered in; new plans would use the new template.

## Validation

We will consider this decision successful if:

1. **Adoption:** Implementers use the change plan template before coding; the template is referenced in implementation tasks or tickets.

2. **Constraint enforcement:** No accepted change plan is violated during implementation (scope creep is caught in code review and traced back to plan deviation).

3. **Test alignment:** Success criteria from specs map directly to tests and test names align with plan sections.

4. **Clarity:** Reviewers report that change plans are clear and reduce review time by catching scope issues early.

Measurable signals:

- At least 3 completed feature implementations include a filled change plan in the PR description or committed to the repo.

- Zero successful PRs that implement features not explicitly listed in the change plan (or plan was updated before implementation, with rationale).

- At least one code review catches a scope deviation and references the change plan (positive signal: constraint enforcement working).

- Contributor feedback: "The plan template kept me focused and helped clarify what I needed to build" (or similar).

Review checkpoints:

- After the first 2-3 features using the template: confirm the format is clear and not burdensome; gather feedback on missing sections.

- Quarterly: confirm the template is still aligned with spec and ADR structure (no drift).

- If change plan updates are needed, open a new ADR rather than modifying this one.
