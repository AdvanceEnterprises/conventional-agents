# ADR-0008: Adopt markdownlint for ADR Formatting Consistency

## Status

- Accepted

## Context and Problem Statement

The MADR template (vendor/madr/) includes a `.markdownlint.yml` configuration that enforces consistent markdown formatting for ADRs. This is a known best practice in the MADR community, as documented in MADR's CONTRIBUTING.md.

Currently, conventional-agents has no automated enforcement of markdown formatting:

- **Formatting inconsistency risk (MEDIUM):** Manual review cannot catch all style issues (spacing, heading levels, list formatting, link syntax).

- **Review friction (LOW):** Reviewers must inspect raw markdown and provide style feedback instead of relying on automation.

- **Onboarding friction (LOW):** New contributors must guess formatting conventions instead of having tooling guide them.

- **MADR guidance ignored:** MADR explicitly recommends markdownlint; not using it diverges from upstream best practice.

The core problem: How do we ensure consistent, professional markdown formatting in ADRs without placing the burden on manual code review?

## Decision Drivers

- **Consistency:** All ADRs should follow a uniform markdown style.

- **Automation:** Tooling should catch formatting issues before PR review.

- **Upstream alignment:** MADR template includes a recommended config; we should use it.

- **Low friction:** Tooling should be optional locally but enforced in CI.

- **Clarity:** Formatting rules should be explicit and documented.

## Considered Options

### Option A: No Linting – Manual Review Only

Rely on code reviewers to catch formatting inconsistencies during PR review.

**Pros:**

- No tooling dependency

- No CI configuration needed

- Reviewers make judgment calls on what matters

**Cons:**

- Inconsistent enforcement (some issues missed, others over-corrected)

- Review friction and time spent on style vs. substance

- Easier for contributors to submit non-compliant formatting

- MADR guidance ignored

- No early feedback for contributors (errors caught after PR opened)

### Option B: Adopt markdownlint with MADR-Derived Config (CHOSEN)

Use markdownlint with a configuration adapted from MADR's `.markdownlint.yml`. Enforce in CI; document as optional tooling for local development.

**Pros:**

- Automated, consistent formatting checks

- Early feedback to contributors (before PR)

- Aligns with MADR upstream best practice

- CI gate prevents non-compliant ADRs from merging

- Config is minimal (only 2 rules disabled: MD013, MD024)

- Optional tooling for local use doesn't block contributors without npm

- Clear, auditable formatting rules

**Cons:**

- Requires npm/node tooling (optional but recommended)

- Adds CI step and build time (minimal)

- Configuration file to maintain (low overhead)

- Contributors must install markdownlint locally to avoid CI failures (mitigated by clear docs)

### Option C: Manual Review Checklist Only

Create a formatting checklist in docs/decisions/README.md and rely on reviewer discipline to apply it.

**Pros:**

- No tooling dependency

- Explicit rules documented

**Cons:**

- Manual process scales poorly

- Inconsistent enforcement (human error)

- No early feedback for contributors

- More reviewer burden than automated tooling

- Checklist easily forgotten or deprioritized

### Option D: Use Alternative Linting Tool (Prettier)

Use Prettier or another markdown formatter instead of markdownlint.

**Pros:**

- More opinionated formatting

- Auto-fix capability (markdownlint is lint-only)

**Cons:**

- Diverges from MADR recommendation

- Overkill for this use case (we want consistency, not aggressive reformatting)

- Prettier less mature for markdown than for code

- Configuration tuning more complex

- Not the MADR standard

## Decision Outcome

Chosen option: **Option B (Adopt markdownlint with MADR-Derived Config)**.

Rationale:

- MADR explicitly recommends markdownlint; we should follow upstream best practice.

- Automated tooling is more reliable than manual review for style consistency.

- The configuration is minimal (2 disabled rules) and well-understood.

- CI enforcement ensures compliance; local use is optional but encouraged.

- Low overhead and minimal maintenance burden.

### Implementation

**Configuration:**

- Copy or reference `vendor/madr/.markdownlint.yml` at `docs/decisions/.markdownlint.yml` or use via npm config.

- Config disables only 2 rules:

  - MD013 (line length): Allow arbitrary length for one-sentence-per-line style

  - MD024 (duplicate headings): Allow repeated headings (Options, Consequences, etc.) and titles

**Tooling Setup:**

- Add markdownlint to project dependencies (devDependencies in package.json if present, or via docker/CI).

- Document installation and usage in docs/decisions/README.md.

- Add CI check to run markdownlint on docs/decisions/*.md.

**Developer Workflow:**

- Local: `npm install && npx markdownlint docs/decisions/ADR-*.md` (optional)

- CI: Automatically run markdownlint on all ADRs; fail if violations found.

- Pre-commit hook (optional): Could auto-lint but not enforced.

**Scope:**

- Applies to: All ADRs in docs/decisions/ (ADR-0000.md through ADR-XXXX.md).

- Not applied to: Other markdown files in the repo (README.md, INTEGRATION.md, etc.) unless explicitly decided.

## Consequences

### Positive

- Formatting consistency is guaranteed and auditable.

- Contributors get immediate feedback on formatting before PR review.

- CI gate prevents style regressions.

- Aligns with MADR upstream best practice and community conventions.

- Low configuration overhead (2-line config).

- Reviewers can focus on substance, not formatting.

- New contributors can run linting locally to self-correct.

### Negative

- Adds tooling dependency (npm/node must be available in CI).

- Slight CI build time increase (markdownlint is very fast, <1 second typically).

- Contributors must install npm/markdownlint to catch errors locally (mitigated by CI feedback).

- If markdownlint becomes unmaintained, we'll need to migrate to alternative.

**Mitigations:**

- Document setup clearly in docs/decisions/README.md with one-liner install command.

- Markdownlint is widely used and actively maintained (low abandonment risk).

- Configuration is simple and portable; easy to migrate to alternative if needed.

### Neutral

- This decision does not affect ADR content, only formatting.

- Existing ADRs may need one-time reformatting to comply.

- Rules are well-documented in MADR upstream; no proprietary linting rules.

## Validation

We will consider this decision successful if:

1. **Tooling Setup:**

   - `.markdownlint.yml` configuration exists and is documented.

   - markdownlint is in CI pipeline and runs automatically on ADRs.

   - Local setup instructions exist in docs/decisions/README.md.

2. **Compliance:**

   - All existing ADRs (ADR-0000 through ADR-0007) pass markdownlint without violations.

   - All new ADRs submitted in PRs pass linting before merge.

3. **Documentation:**

   - docs/decisions/README.md includes: setup command, how to run locally, what to do if linting fails.

   - Troubleshooting section explains common violations and fixes.

4. **Process Integration:**

   - CI check fails and provides readable error message if ADR violates linting rules.

   - Contributors are not blocked; they can quickly fix and re-push.

**Measurable Signals:**

- All ADRs in docs/decisions/ pass `markdownlint docs/decisions/ADR-*.md` without warnings or errors.

- At least 1 PR includes a lint-fix commit addressing formatting issues caught by markdownlint.

- Zero formatting-related review comments on new ADRs (linting caught them first).

**Review Checkpoints:**

- After first ADR PR using linting: confirm process works smoothly and feedback is clear.

- Quarterly: confirm linting is still passing and no rules need adjustment.

- If markdownlint becomes unmaintained: revisit and decide on alternative.
