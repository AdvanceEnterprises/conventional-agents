## Context and Problem Statement

ADR-0013 establishes the coordination primitives for multi-session work: primary vs. contributor mode, parallel-primary scope rules, attribution trailers, escalation rules. FS-0014 defines the six-role taxonomy. FS-0015 defines five session modes and the explainability convention.

These documents answer *who has authority* and *how roles relate*. They do not answer:

1. How a contributor session's output is structured so that the primary can synthesize multiple contributors without re-reading prose and re-deriving claims.
2. How the synthesis is quality-checked before the primary commits it.
3. How contributors receive the same prompt framing regardless of which model fills the contributor slot, so that cross-model consensus is genuinely comparable rather than artifact of model-specific prompt sensitivity.
4. How this orchestration is invoked by an operator in a way that does not collapse back into "just paste the question into three windows."
5. **How contributors with different invocation transports (external CLI vs Hermes chat) participate in the same task under consistent attribution and contract rules** (added 2026-06-25).

Without operational answers to these questions, the framework's multi-session capability is theoretical. The conventional-agents framework's value depends on multi-session work being reproducible, auditable, and not the result of operator improvisation.

The core problem: when multiple models are invited to provide input on the same task — across any combination of external CLIs (e.g., Claude Code, Codex CLI) and Hermes-invoked providers (e.g., `qwen3-coder-next`, `devstral2` via `hermes chat`) — how is the orchestration structured so that the inputs are comparable, the synthesis is gate-evaluated, and the artifacts carry forward to ADR-0013's merge gate with full attribution?

**Operational reality (2026-06-24, updated 2026-06-25):** Until and beyond Hermes Agent's direct integration with vendor CLIs, contributors can be invoked through two transports: (a) external CLI windows on the operator's workstation (paste a rendered prompt into Claude Code or Codex CLI), and (b) Hermes-internal invocation (`hermes chat -m MODEL --provider PROVIDER --toolsets ...`). The orchestration pattern documented here supports both transports uniformly. External-CLI contributors receive paste-ready prompts; Hermes-internal contributors are invoked via Hermes chat calls. The contributor prompt template uses a render-mode parameter to distinguish these.

The pattern remains **operator-driven** even with Hermes-internal contributors: the operator decides the contributor set, runs (or instructs Hermes to run) each contributor, captures outputs, and produces the synthesis themselves. When Hermes gains broader autonomy over orchestration, the templates and helper scripts make that transition mechanical rather than re-designed.

## Decision Drivers

- **Structured-output comparability.** Contributor outputs in the same prompt must produce the same shape across models so that the primary can synthesize them mechanically. Without this, "consensus" becomes the primary's editorial impression, not an auditable signal.
- **Independent quality gate.** The synthesis step must be evaluated by a model independent of the contributor set. This is what prevents the primary from "grading its own work" when incorporating contributor outputs.
- **ADR-0013 compliance.** Any operational pattern must respect the primary/contributor rules, the parallel-primary scope rules, the attribution trailer conventions, and the human-escalation rules. The orchestration is *on top of* ADR-0013, not a parallel mechanism.
- **FS-0014/0015 compliance.** Role assignments follow the six-role taxonomy; session mode declarations follow FS-0015's explainability convention. The orchestration does not invent new roles or modes. **In particular, FS-0015 requires declaring *all* supporting roles, not a single `contributor_role`** (added 2026-06-25 per PR #62 reviewer finding).
- **Operator ergonomics.** The pattern must be invokable by a single operator (Tai) without orchestrating real-time coordination across CLIs or across Hermes chat sessions. The contributor prompt template is the operator's lever.
- **Render-mode portability.** Contributors invoked through different transports (external CLI vs Hermes chat) must produce comparable outputs under the same attribution rules. The render-mode parameter separates the *who* (model) from the *how* (transport).
- **Cost-aware.** Cross-model orchestration is more expensive than single-model work. The pattern must default to lightweight (synthesis only) and escalate to gated (independent evaluator) only when stakes justify it.

## Considered Options

### Option A: Ad-hoc orchestration, no template

Operator pastes the prompt into multiple CLIs/Hermes chat sessions by hand, copies outputs into a synthesis document, writes the synthesis themselves.

**Pros:** Zero new infrastructure. Works today. Operator retains full editorial control.

**Cons:** Reproducibility is operator-dependent; outputs cannot be re-derived. Cross-model differences in prompt sensitivity contaminate "consensus." Synthesis quality is operator skill-dependent. No attribution trail beyond the operator's claim. Does not scale to a contributor count above three.

### Option B: Multi-model library (e.g., OpenAI evals, custom orchestrator)

Build a Hermes-side orchestrator that calls each model with the same prompt and produces a synthesis document.

**Pros:** Reproducible invocations. Clean attribution. Could be invoked from CI.

**Cons:** Real-time infrastructure, which ADR-0013 deliberately rejects in favor of document-driven coordination. Requires maintaining a new tool against the risk that any of the model CLIs change shape. Diverges from ADR-0013's git-as-coordination principle. Significant scope creep for the conventional-agents framework, which is supposed to be standards + governance, not workflow orchestration.

### Option C: Document-driven orchestration with structured output and gate evaluator (CHOSEN)

A reusable contributor prompt template (`templates/contributor/contributor-prompt.md`) combines the ADR-0013 transparency statement, the FS-0015 role/mode declaration (including *all* supporting roles, not a single role), and a structured-output contract. The template supports multiple render modes (external CLI vs Hermes-internal invocation) and per-contributor parameters (role, contract, attribution). The operator (or Hermes, on behalf of the operator) invokes each contributor; the operator produces the synthesis; an independent evaluator model emits a gate verdict before commit.

**Pros:**

- Reproducible: every contributor receives the same prompt template.
- Document-driven: the prompt template, the synthesis, and the gate verdict are all durable artifacts in the repo.
- ADR-0013 compliant: contributors do not commit, primary holds commit authority, attribution trailers carry through.
- FS-0014/0015 compliant: full supporting-role declaration is baked into the template.
- Render-mode portable: same template renders correctly for external CLIs and Hermes-internal invocations.
- Cost-aware: gate evaluator is opt-in per task; the default is synthesis-only.
- Skill-reuse: uses existing `claude-code`, `codex`, and Hermes chat patterns without inventing new vendor-specific glue.

**Cons:**

- Three artifacts to maintain (template, synthesis template, gate template) — small but real overhead.
- Gate evaluator assumes a working independent model is configured (currently `deepseek-v4-pro` via `ollama-cloud`; pre-run probe required).
- Template-driven orchestration is still operator-invoked; not autonomous. Acceptable per ADR-0013's deliberate rejection of real-time infrastructure.
- Mixed contract types across contributors require the primary synthesis to do extra work to reconcile them. **The framework mitigates this by requiring every contributor output to expose a shared claim envelope** (claim ID, statement, citation, contributor position, confidence) regardless of whether the contract is Research Brief or JSON schema (added 2026-06-25 per PR #62 reviewer finding).

### Option D: Vendor-specific orchestration (one CLI per model, hand-coordinated)

Treat each model as its own orchestration system with no shared template.

**Pros:** No new artifacts to maintain.

**Cons:** Reproducibility breaks per-vendor. "Same prompt to all contributors" is operator-dependent. ADR-0013 attribution becomes harder to enforce uniformly. Render-mode plumbing has to be re-invented per vendor.

## Decision Outcome

**Chosen option: Option C — Document-driven orchestration with structured output and gate evaluator.**

The pattern is:

1. **Operator names the task** and picks: target artifact, session mode (per FS-0015), primary session, **contributor set** (per-target parameters: model, render mode, role, contract, attribution label), and gate mode (synthesis-only or full-gate).
2. **Operator invokes the contributor prompt template** (`templates/contributor/contributor-prompt.md`) for each contributor. The template is parameterized by task framing, session mode, primary role, supporting roles, render mode, and per-contributor structured-output contract.
3. **Each contributor runs in its assigned transport** (external CLI window or `hermes chat` invocation per its render mode), produces its output in the contracted format, and posts the output as a PR comment on the primary's branch (per ADR-0013 attribution rule). Contributors do not commit to the primary's branch.
4. **The operator produces the synthesis** in `docs/orchestration/<task-id>-synthesis.md` using the synthesis template. The synthesis has five mandatory sections (Coverage/Disposition Record, Consensus, Divergent Points, Unique Insights, Recommended Action) per the 2026-06-25 update; an attribution plan follows at the end. See `templates/contributor/synthesis-template.md` for the canonical structure.
5. **If gate mode is `full-gate`**, an independent evaluator model (default: `deepseek-v4-pro` per `action-framework-research`) reads the contributor outputs and the synthesis and emits a gate execution status (`COMPLETE` / `NOT_RUN` / `INVALID`) followed by a gate verdict (`PROCEED` / `CONDITIONAL` / `HALT`) on `COMPLETE`. The verdict is captured in `docs/orchestration/<task-id>-gate.md`.
6. **Operator approves** the synthesis (or sends it back for revision). The primary session commits with `Assisted-By:` and `Contributor-Session:` trailers per ADR-0013.
7. **Pilot validation.** Before this ADR is accepted, a pilot (PLAN-0016) must run end-to-end against a small, low-stakes task. The pilot's evidence is used to revise this ADR and (if appropriate) accept it.

### Render Modes

The contributor prompt template supports three render modes (added 2026-06-25):

- **`external-cli`**. Contributor is invoked through an external CLI window on the operator's workstation (e.g., Claude Code, Codex CLI). The rendered prompt is paste-ready text. Attribution trailer: `Assisted-By: <model name>` (the model itself, not Hermes).
- **`hermes-chat`**. Contributor is invoked through Hermes (`hermes chat -m MODEL --provider PROVIDER --toolsets ...`). The rendered prompt is an invocation block the operator can paste into a terminal or that Hermes can execute on the operator's behalf. Attribution trailer: `Assisted-By: hermes (<model name>)` to reflect that Hermes drove the invocation, not the model directly.
- **`research-pass`**. Contributor is invoked for survey or opinion work; no FS-0015 transparency block is required and the contributor output is treated as advisory input rather than an accountable contributor session. The framework requires this mode to be declared explicitly per contributor, not asserted in template comments. Attribution trailer: `Assisted-By: hermes (<model name>)` (research pass is always Hermes-internal).

The render mode is a per-contributor parameter. The same template renders correctly for all three modes; the rendered output differs in transport details but not in the underlying contract, framing, or attribution rules.

### Structured Output Contract

Two contract types are first-class:

- **Research Brief** (freeform markdown, defined in `references/research-brief-template.md`): used for architecture, design, ADR/FS drafting, and other tasks where prose synthesis is the natural shape.
- **JSON schema** (machine-parseable, defined per task): used for code review observations, implementation proposals, and other tasks where downstream tooling consumes the output.

The contract is a **per-contributor parameter**, not a per-task parameter. Mixing contract types across contributors for the same task is the expected case (e.g., one contributor produces a JSON-schema code review, another produces a Research Brief on architecture tradeoffs); the primary synthesis reconciles them via the shared claim envelope.

**Shared claim envelope (added 2026-06-25 per PR #62 reviewer finding):** Regardless of contract type, every contributor output must expose, at minimum:

- `claim_id`: a stable identifier (e.g., `C-CLAUDE-001`).
- `statement`: the claim itself.
- `source_citation`: the input source the claim derives from.
- `contributor_position`: the contributor's stance (affirm / disagree / silent / out-of-scope).
- `confidence`: the contributor's self-rated confidence.

For Research Brief contracts, these appear as table columns or footnote-style annotations. For JSON-schema contracts, they appear as top-level fields. The synthesis template consumes the envelope, not the raw prose or raw JSON.

### Gate Mode and Execution Status

Default: **synthesis-only** (skip the evaluator gate). Used for tasks where the operator is willing to accept the primary's editorial synthesis.

Escalate to **full-gate** when:

- The task touches an accepted ADR or modifies the framework itself.
- Two or more contributors produced divergent outputs on the same claim.
- The synthesis makes a recommendation that contradicts an existing ADR.
- The operator explicitly requests a gate.

**Gate execution status (added 2026-06-25 per PR #62 reviewer finding):** The gate has two layers:

- **Execution status** describes whether the gate ran successfully: `COMPLETE` (gate ran and produced a verdict), `NOT_RUN` (gate was skipped or probe failed), `INVALID` (gate ran but produced a malformed response). Status `NOT_RUN` and `INVALID` are *not* verdicts; they signal that no verdict was issued.
- **Verdict** describes the gate's evaluation when status is `COMPLETE`: `PROCEED` / `CONDITIONAL` / `HALT`.

The pre-run probe pattern from `action-framework-research` (verify the gate model responds) is required before relying on the gate evaluator.

**Gate independence (added 2026-06-25):** The gate model must not appear in the contributor set for the same task. The contributor prompt helper script enforces this as a static check (`scripts/render_contributor_prompt.py:_validate`); an `--allow-gate-overlap` flag exists for the operator to override when there is a specific reason.

### What this ADR does NOT do

- **It does not create a real-time orchestrator.** Coordination is document-driven per ADR-0013.
- **It does not add new roles or session modes.** It uses FS-0014's six roles and FS-0015's five modes.
- **It does not override ADR-0013's human-escalation rule.** Conflicts escalate to the operator; the gate is *additional*, not a replacement.
- **It does not name a specific contributor set.** The framework specifies what counts as a contributor and how contributors are invoked; concrete contributor sets are per-pilot parameters in the task's parameter file.
- **It does not standardize cross-vendor CLI invocation.** Vendor CLIs are invoked per their existing skills; the orchestration is at the prompt-template level.

## Consequences

### Positive

- Cross-model consensus becomes auditable: contributor outputs are saved as durable artifacts in the orchestration directory.
- The synthesis template prevents silent averaging — divergent points are preserved, not flattened. The coverage/disposition record prevents partial coverage from being labeled as consensus.
- The gate evaluator catches the failure mode where the primary over-trusts its own synthesis. Gate execution status separates "evaluator unreachable" from "evaluator rejected."
- Attribution trailers from ADR-0013 carry through unchanged, with a per-render-mode convention that distinguishes direct CLI invocation from Hermes-driven invocation.
- The pattern is reusable across conventional-agents, feral-fleet, and any other vendored project.
- The framework is render-mode-agnostic: external-CLI and Hermes-internal contributors participate under the same contract, attribution, and gate rules.

### Negative

- Three artifacts to maintain (`templates/contributor/contributor-prompt.md`, `templates/contributor/synthesis-template.md`, `templates/contributor/gate-template.md`).
- Gate evaluator requires a configured independent model; if unavailable, the pattern degrades to synthesis-only without notice (the operator must check).
- The operator still has to invoke contributors; this is not autonomous orchestration.
- Cross-vendor output contracts (Research Brief vs. JSON schema) require the primary synthesis to do extra work to reconcile them via the shared claim envelope.
- The shared claim envelope adds per-contributor overhead (every claim must carry the envelope fields).

### Neutral

- Existing ADR-0013, FS-0014, FS-0015 do not change. This ADR is additive.
- Per-pilot contributor availability (which models are configured, which CLIs are installed on the operator's workstation) determines which render modes are usable. The orchestration is portable across vendors but not invariant.

## Validation

We will consider this ADR successful if:

1. **Pilot completion.** PLAN-0016 runs end-to-end against a small, low-stakes task in conventional-agents or feral-fleet. The pilot produces: contributor outputs in at least one contract type, a synthesis document with coverage/disposition record, a gate verdict (or explicit NOT_RUN status), and a committed artifact with `Assisted-By:` trailers.
2. **Template usability across render modes.** The contributor prompt template produces correct output for at least one `external-cli` contributor and at least one `hermes-chat` contributor in the same task, with per-contributor parameters (role, contract, attribution) honored.
3. **Gate evaluator reliability.** The independent gate model is reachable via the configured provider; the pre-run probe pattern works; gate execution status is correctly distinguished from gate verdict.
4. **Cross-vendor attribution.** Final commits carry `Assisted-By:` and `Contributor-Session:` trailers that identify which model produced which contributor output, with render-mode-appropriate attribution format.
5. **ADR-0013 compatibility.** No contributor session commits to the primary's branch. No contributor session opens a PR on behalf of the task. No contributor session transitions a governed document's status. These are testable from git history.

Measurable signals:

- One PR per pilot run with at least one `Assisted-By:` trailer per contributor.
- One synthesis document (with coverage/disposition record) and (in full-gate mode) one gate verdict per pilot run, both committed.
- Zero contributor commits to the primary's branch in pilot PR history.
- Zero FS-0015 explainability-convention violations in pilot PR descriptions (every contributor session declares mode + primary role + all supporting roles at start).

Review checkpoints:

- After first pilot run: revise the contributor prompt template based on what actually worked across render modes.
- After three pilot runs: evaluate whether full-gate mode is needed for the typical case, or whether synthesis-only is sufficient.
- Quarterly: review whether the structured-output contract types need expansion (e.g., a YAML schema variant) and whether the shared claim envelope needs adjustment.
