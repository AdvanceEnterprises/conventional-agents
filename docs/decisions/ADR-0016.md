# ADR-0016: Multi-model session orchestration with structured output and gate evaluation

## Status

- Proposed (awaiting first end-to-end pilot before acceptance; see `docs/change-plans/PLAN-0016-multi-model-pilot.md`)

## Context and Problem Statement

ADR-0013 establishes the coordination primitives for multi-session work: primary vs. contributor mode, parallel-primary scope rules, attribution trailers, escalation rules. FS-0014 defines the six-role taxonomy. FS-0015 defines five session modes and the explainability convention.

These documents answer *who has authority* and *how roles relate*. They do not answer:

1. How a contributor session's output is structured so that the primary can synthesize multiple contributors without re-reading prose and re-deriving claims.
2. How the synthesis is quality-checked before the primary commits it.
3. How contributors receive the same prompt framing regardless of which model fills the contributor slot, so that cross-model consensus is genuinely comparable rather than artifact of model-specific prompt sensitivity.
4. How this orchestration is invoked by an operator (you) in a way that does not collapse back into "just paste the question into three windows."

Without operational answers to these questions, the framework's multi-session capability is theoretical. The conventional-agents framework's value depends on multi-session work being reproducible, auditable, and not the result of operator improvisation.

The core problem: when multiple models are invited to provide input on the same task — Codex (implementation), Claude (architect/reviewer), Gemini (research) — how is the orchestration structured so that the inputs are comparable, the synthesis is gate-evaluated, and the artifacts carry forward to ADR-0013's merge gate with full attribution?

**Operational reality (2026-06-24):** Until Hermes Agent gains direct integration with vendor CLIs (Claude Code, Codex CLI, Gemini CLI), the operator invokes each model manually. The orchestration pattern documented here is **operator-driven**: the operator pastes a rendered prompt into each CLI, captures the output, and produces the synthesis themselves. The templates and the helper script defined by this ADR make this manual orchestration reproducible and auditable so that when Hermes gains direct integration, the same artifacts can be produced automatically without re-designing the pattern.

## Decision Drivers

- **Structured-output comparability.** Contributor outputs in the same prompt must produce the same shape across models so that the primary can synthesize them mechanically. Without this, "consensus" becomes the primary's editorial impression, not an auditable signal.
- **Independent quality gate.** The synthesis step must be evaluated by a model independent of the contributor set. This is what prevents the primary from "grading its own work" when incorporating contributor outputs.
- **ADR-0013 compliance.** Any operational pattern must respect the primary/contributor rules, the parallel-primary scope rules, the attribution trailer conventions, and the human-escalation rules. The orchestration is *on top of* ADR-0013, not a parallel mechanism.
- **FS-0014/0015 compliance.** Role assignments follow the six-role taxonomy; session mode declarations follow FS-0015's explainability convention. The orchestration does not invent new roles or modes.
- **Operator ergonomics.** The pattern must be invokable by a single operator (Tai) without orchestrating real-time coordination across CLIs. The contributor prompt template is the operator's lever.
- **Cost-aware.** Cross-model orchestration is more expensive than single-model work. The pattern must default to lightweight (synthesis only) and escalate to gated (independent evaluator) only when stakes justify it.

## Considered Options

### Option A: Ad-hoc orchestration, no template

Operator pastes the prompt into three CLIs by hand, copies outputs into a synthesis document, writes the synthesis themselves.

**Pros:**
- Zero new infrastructure.
- Works today.
- Operator retains full editorial control.

**Cons:**
- Reproducibility is operator-dependent; outputs cannot be re-derived.
- Cross-model differences in prompt sensitivity contaminate "consensus."
- Synthesis quality is operator skill-dependent.
- No attribution trail beyond the operator's claim.
- Does not scale to a future where contributor count grows past three.

### Option B: Multi-model library (e.g., OpenAI evals, custom orchestrator)

Build a Hermes-side orchestrator that calls each model with the same prompt and produces a synthesis document.

**Pros:**
- Reproducible invocations.
- Clean attribution.
- Could be invoked from CI.

**Cons:**
- Real-time infrastructure, which ADR-0013 deliberately rejects in favor of document-driven coordination.
- Requires maintaining a new tool against the risk that any of the model CLIs change shape.
- Diverges from ADR-0013's git-as-coordination principle.
- Significant scope creep for the conventional-agents framework, which is supposed to be standards + governance, not workflow orchestration.

### Option C: Document-driven orchestration with structured output and gate evaluator (CHOSEN)

A reusable contributor prompt template (`templates/contributor/contributor-prompt.md`) combines the ADR-0013 transparency statement, the FS-0015 role/mode declaration, and a structured-output contract. The primary session runs each contributor via the existing per-vendor skills (`claude-code`, `codex`, plus a research-pass invocation for Gemini per `action-framework-research`). The primary session synthesizes; an independent evaluator model (`deepseek-v4-pro` per `action-framework-research`) gate-evaluates the synthesis before commit.

**Pros:**
- Reproducible: every contributor receives the same prompt template.
- Document-driven: the prompt template, the synthesis, and the gate verdict are all durable artifacts in the repo.
- ADR-0013 compliant: contributors do not commit, primary holds commit authority, attribution trailers carry through.
- FS-0014/0015 compliant: role + session mode declarations are baked into the template.
- Cost-aware: gate evaluator is opt-in per task; the default is synthesis-only.
- Skill-reuse: no new vendor-specific glue; uses existing `claude-code`, `codex`, and `action-framework-research` skills.

**Cons:**
- Three artifacts to maintain (template, synthesis template, gate template) — small but real overhead.
- Gate evaluator assumes a working `deepseek-v4-pro` provider is configured (currently `ollama-cloud`; pre-run probe required).
- Template-driven orchestration is still operator-invoked; not autonomous. Acceptable per ADR-0013's deliberate rejection of real-time infrastructure.
- Cross-vendor output contracts differ: Research Brief (freeform markdown) vs. JSON schema (machine-parseable). Templates must respect this rather than force uniformity.

### Option D: Vendor-specific orchestration (one CLI per model, hand-coordinated)

Treat Claude Code, Codex, and Gemini as separate orchestration systems. Operator runs each through its own skill, with no shared template.

**Pros:**
- No new artifacts to maintain.

**Cons:**
- Reproducibility breaks per-vendor.
- "Same prompt to all three" is operator-dependent.
- ADR-0013 attribution becomes harder to enforce uniformly.

## Decision Outcome

**Chosen option: Option C — Document-driven orchestration with structured output and gate evaluator.**

The pattern is:

1. **Operator names the task** and picks: target artifact, session mode (per FS-0015), primary session (which model fills which role), contributor set (which models add input in which supporting roles), and gate mode (synthesis-only or full-gate).
2. **Operator invokes the contributor prompt template** (`templates/contributor/contributor-prompt.md`) for each contributor. The template is parameterized by task framing, session mode, primary role, supporting roles, and structured-output contract (Research Brief for design/architecture, JSON schema for code/implementation).
3. **Each contributor runs in a worktree** (per the `codex` skill's parallel-worktree pattern), produces its output in the contracted format, and posts the output as a PR comment on the primary's branch (per ADR-0013 attribution rule). Contributors do not commit to the primary's branch.
4. **The primary session synthesizes** the contributor outputs in a synthesis document (`docs/orchestration/<task-id>-synthesis.md`). The synthesis must use a specific structure (defined in the synthesis template): consensus points, divergent points, unique insights, recommended action.
5. **If gate mode is `full-gate`**, an independent evaluator model (default: `deepseek-v4-pro` per `action-framework-research`) reads the contributor outputs and the synthesis and emits a gate verdict: `PROCEED` / `CONDITIONAL` / `HALT`. The verdict is captured in `docs/orchestration/<task-id>-gate.md`.
6. **Operator approves** the synthesis (or sends it back for revision). The primary session commits with `Assisted-By:` and `Contributor-Session:` trailers per ADR-0013.
7. **Pilot validation.** Before this ADR is accepted, a pilot (PLAN-0016) must run end-to-end against a small, low-stakes task. The pilot's evidence is used to revise this ADR and (if appropriate) accept it.

### Structured Output Contract

Two contract types are first-class:

- **Research Brief** (freeform markdown, defined in `action-framework-research` skill): used for architecture, design, ADR/FS drafting, and other tasks where prose synthesis is the natural shape.
- **JSON schema** (machine-parseable, defined per task): used for code review observations, implementation proposals, and other tasks where downstream tooling consumes the output.

The contributor prompt template selects one contract per task. Mixing contract types across contributors for the same task is allowed (e.g., one contributor produces a JSON-schema code review, another produces a Research Brief on architecture tradeoffs) but the primary synthesis must reconcile them.

### Gate Mode Defaults

Default: **synthesis-only** (skip the evaluator gate). Used for tasks where the operator is willing to accept the primary's editorial synthesis.

Escalate to **full-gate** when:

- The task touches an accepted ADR or modifies the framework itself.
- Two or more contributors produced divergent outputs on the same claim.
- The synthesis makes a recommendation that contradicts an existing ADR.
- The operator explicitly requests a gate.

The pre-run probe pattern from `action-framework-research` (verify `deepseek-v4-pro` responds) is required before relying on the gate evaluator.

### What this ADR does NOT do

- **It does not create a real-time orchestrator.** Coordination is document-driven per ADR-0013.
- **It does not add new roles or session modes.** It uses FS-0014's six roles and FS-0015's five modes.
- **It does not override ADR-0013's human-escalation rule.** Conflicts escalate to the operator; the gate is *additional*, not a replacement.
- **It does not standardize cross-vendor CLI invocation.** Vendor CLIs are invoked per their existing skills; the orchestration is at the prompt-template level.

## Consequences

### Positive

- Cross-model consensus becomes auditable: contributor outputs are saved as durable artifacts in the orchestration directory.
- The synthesis template prevents silent averaging — divergent points are preserved, not flattened.
- The gate evaluator catches the failure mode where the primary over-trusts its own synthesis.
- Attribution trailers from ADR-0013 carry through unchanged.
- The pattern is reusable across conventional-agents, feral-fleet, and any other vendored project.

### Negative

- Three artifacts to maintain (`templates/contributor/contributor-prompt.md`, `templates/contributor/synthesis-template.md`, `templates/contributor/gate-template.md`).
- Gate evaluator requires `deepseek-v4-pro` provider to be configured; if unavailable, the pattern degrades to synthesis-only without notice (the operator must check).
- The operator still has to invoke contributors; this is not autonomous orchestration.
- Cross-vendor output contracts (Research Brief vs. JSON schema) require the primary synthesis to do extra work to reconcile them.

### Neutral

- Existing ADR-0013, FS-0014, FS-0015 do not change. This ADR is additive.
- Per-project vendor availability (Claude Code, Codex CLI, Gemini CLI) determines which contributors can fill which roles. The orchestration is portable across vendors but not invariant.

## Validation

We will consider this ADR successful if:

1. **Pilot completion.** PLAN-0016 runs end-to-end against a small, low-stakes task in conventional-agents or feral-fleet. The pilot produces: contributor outputs in two formats, a synthesis document, a gate verdict, and a committed artifact with `Assisted-By:` trailers.
2. **Template usability.** The contributor prompt template can be invoked with task parameters and produces a prompt that each vendor's CLI accepts without manual rewriting.
3. **Gate evaluator reliability.** The `deepseek-v4-pro` gate evaluator is reachable via the configured provider; the pre-run probe pattern works; gate verdicts are correctly categorized (`PROCEED` / `CONDITIONAL` / `HALT`).
4. **Cross-vendor attribution.** Final commits carry `Assisted-By:` and `Contributor-Session:` trailers that identify which model produced which contributor output.
5. **ADR-0013 compatibility.** No contributor session commits to the primary's branch. No contributor session opens a PR on behalf of the task. No contributor session transitions a governed document's status. These are testable from git history.

Measurable signals:

- One PR per pilot run with at least one `Assisted-By:` trailer.
- One synthesis document and (in full-gate mode) one gate verdict per pilot run, both committed.
- Zero contributor commits to the primary's branch in pilot PR history.
- Zero ADR-0013 explainability-convention violations in pilot PR descriptions (per FS-0015, each session must declare its mode + primary role + supporting roles at start).

Review checkpoints:

- After first pilot run: revise the contributor prompt template based on what actually worked.
- After three pilot runs: evaluate whether full-gate mode is needed for the typical case, or whether synthesis-only is sufficient.
- Quarterly: review whether the structured-output contract types need expansion (e.g., a YAML schema variant).
